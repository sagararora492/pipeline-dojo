A running total looks like the easiest window function there is: add an
`ORDER BY` inside `OVER` and the sum accumulates. It works until two rows share
the same ordering value. Then both rows show the same total, and nothing warns
you.

The `payments` table below is used throughout. Account A made two payments on
2024-07-03.

| payment_id | account_id | paid_on | amount |
|---|---|---|---|
| 1 | A | 2024-07-01 | 100.00 |
| 2 | A | 2024-07-03 | 40.00 |
| 3 | A | 2024-07-03 | 60.00 |
| 4 | A | 2024-07-05 | 25.00 |
| 5 | B | 2024-07-02 | 500.00 |
| 6 | B | 2024-07-04 | 250.00 |

## The frame decides which rows are summed

A window function sees a **frame**: a set of rows around the current row,
inside its partition. If you don't write a frame, you get a default, and the
default depends on whether there is an `ORDER BY`:

- **No `ORDER BY`:** the frame is the whole partition.
  `sum(amount) OVER (PARTITION BY account_id)` puts the account's total on
  every row.
- **With `ORDER BY`:** the frame is
  `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.

That second default is what makes a running total. It also holds the trap. In
`RANGE` mode, "current row" means the current row **and its peers**: every row
with the same `ORDER BY` value. The PostgreSQL docs describe the default frame
as running from the partition start "up through the current row's last
`ORDER BY` peer".

```sql
SELECT payment_id, amount,
       sum(amount) OVER (PARTITION BY account_id ORDER BY paid_on) AS running_total
FROM payments
WHERE account_id = 'A';
-- 1 | 100.00 | 100.00
-- 2 |  40.00 | 200.00   <- already includes payment 3
-- 3 |  60.00 | 200.00
-- 4 |  25.00 | 225.00
```

Payments 2 and 3 are peers, so each one's frame includes the other.

## Fix it with a tie-breaker and a `ROWS` frame

In `ROWS` mode, "current row" means just the current row. Add a tie-breaker so
the order is fully decided, and write the frame out:

```sql
sum(amount) OVER (
  PARTITION BY account_id
  ORDER BY paid_on, payment_id
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

You need both parts. A `ROWS` frame without the tie-breaker stops at the
current row, but nothing says whether payment 2 or payment 3 comes first, so
the totals can differ from one run to the next. The tie-breaker without the
`ROWS` frame gives the right answer here, because no two rows are peers any
more. Writing the frame as well means the query says what you meant.

## `lag()`: look at the previous row

`lag(x)` returns `x` from the previous row of the partition, in the window's
`ORDER BY` order. `lead(x)` returns it from the next row. Both take an optional
offset, which defaults to 1, and an optional default value for when there is no
such row, which defaults to NULL.

The first row of each partition has no previous row, so `lag()` returns NULL
there. Keep it. NULL says "there is nothing to compare with", which is
different from "no change". Replacing it with 0 hides that difference.

### Window functions run after `GROUP BY`

To compare one *day* with the previous day, you first need one row per day.
Window functions are computed after grouping and aggregation, so you can pass
an aggregate to one in the same query:

```sql
SELECT account_id, paid_on,
       sum(amount) AS day_total,
       lag(sum(amount)) OVER (PARTITION BY account_id ORDER BY paid_on) AS previous_day_total
FROM payments
GROUP BY account_id, paid_on;
```

The PostgreSQL docs put it this way: it is valid to include an aggregate
function call in the arguments of a window function, but not the other way
round.

## In other databases

| Database | Default frame with `ORDER BY` | `lag(x)` defaults |
|---|---|---|
| DuckDB | `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` | offset 1, default NULL |
| PostgreSQL 18 | `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` | offset 1, default NULL |
| Snowflake | `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` for functions such as `SUM`, `COUNT`, `MIN` and `MAX` | offset 1, default NULL |
| BigQuery | `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` | offset 1, default NULL |

All four document the same default frame, so the tied-rows trap is not a DuckDB
quirk. The DuckDB and PostgreSQL docs state that the frame includes the current
row's peers. [VERIFY: the Snowflake and BigQuery pages give the same default
frame but don't describe tied rows in words.]

Snowflake's `LAG` syntax requires an `ORDER BY` in the `OVER` clause.
